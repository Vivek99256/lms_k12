**Scope:** Frontend `d:\lms_k12` (Next.js), Backend `D:\next_lms_erp\app\Http\Controllers` (Laravel).
**Method:** direct file reads + line-cited grep/glob across both codebases. Every claim below is either (a) confirmed by reading the cited line(s) directly in this pass, or (b) marked **[inferred]** where behavior was not directly executed/observed (e.g. no live tenant data was queried — the app was not run).

## 0. Core mechanics (referenced throughout)

- **Role resolution (frontend dashboard):** `app/dashboard/_lib/resolveDashboardRole.ts:3-5` — `TEACHER_PROFILES = new Set(['teacher', 'lms teacher'])`, `STUDENT_PROFILES = new Set(['student'])`, `ADMIN_PROFILES = new Set(['super admin','admin','school admin'])`. Line 15 lower-cases/trims the incoming `user_profile_name`; line 21 **defaults anything unrecognized to `'admin'`**.
- **Menu/sidebar (real RBAC):** `app/hooks/useMenuRights.ts:131-144` — `POST {API_BASE_URL}/api/menu-rights` with `{sub_institute_id, user_id, user_profile_name, user_profile_id, client_id}`; response's `level 1/2/3` arrays go through `buildMenuTree()` (`app/data/menuMappers.ts:192-249`), which resolves each `link` field via `mapApiLinkToRoute()` (`app/data/routeMapper.ts:474-873`) into the actual Next.js path. Sidebar visibility is entirely server-driven — the frontend does not decide what a teacher can see, the backend's `/api/menu-rights` response does.
- **Backend identity:** `RoleDashboardApiController.php:11-21` (class docblock) — identity comes only from `session()`, hydrated by `ApiSessionHydrator` from the JWT; a client-supplied `user_id`/role is never trusted **in this specific controller**. This guarantee does **not** hold codebase-wide — see §2.
- **Backend auth gate for Teacher dashboard:** `RoleDashboardApiController.php:188-192` — `$profileName = strtolower(trim(session('user_profile_name')))`; rejects unless `$profileName` is in `['teacher','lms teacher']` and `is_student` is falsy.

## 2. Permissions / credentials model

### 2.1 `TEACHER_PROFILES` completeness

- Frontend: `resolveDashboardRole.ts:4` — exactly `{'teacher', 'lms teacher'}`, matched case-insensitively after trim/lowercase (line 15).
- Backend mirror: `RoleDashboardApiController.php:191` — `in_array($profileName, ['teacher', 'lms teacher'], true)`. The two lists are **consistent with each other** today.
- **Ground truth on other teacher variants (Class Teacher, Subject Teacher, HOD, Coordinator, Vice Principal) could not be confirmed from code**: the profile catalog lives in `tbluserprofilemaster` (`D:\next_lms_erp\database\migrations\2023_03_05_115658_create_tbluserprofilemaster_table.php:15-25`), whose `name` column is **tenant-supplied free text** — `tbluserprofilemasterController.php:60,121` takes it straight from `$request->get('profile_name')`. There is no seeder/fixture/SQL dump populating this table in the repo, and no code path treats a profile as "teacher-family" other than an exact string match against `'teacher'`/`'lms teacher'` (there is no `profile_parent_id`-based "is this a teacher-type profile" rule the way `RoleDashboardApiController::isAdminProfile()` does for admins at lines 29-42).
  - **Structural risk (not a confirmed live bug):** any tenant that names a teacher profile anything other than exactly "Teacher" or "Lms Teacher" — e.g. "Class Teacher", "HOD" — would fail both `resolveDashboardRole()` checks and fall into the `admin` default (`resolveDashboardRole.ts:21`), showing that person an Admin dashboard instead of a Teacher one. This can't be confirmed without querying a live tenant's `tbluserprofilemaster` table, which was out of scope for this pass.
- **Confirmed actual bug (unrelated to the above, but same profile-matching family):** `lmsPortfolioController.php:73` compares against `" TEACHER"` (leading space) via `strtoupper()`, while the sibling check at line 42 correctly compares against `"TEACHER"` (no space). A caller whose profile normalizes to exactly "Teacher" will never match line 73's branch, so `getData()` on the LMS Portfolio endpoint silently returns empty `portfolio_data` for a plain "Teacher" profile even though `getPortfolio()`'s own wrapper (line 42) recognizes the same profile correctly elsewhere in the same file.

### 2.2 What "teacher" restricts server-side — scoping audit

**Correctly scoped to the teacher's own assignment (`class_teacher`/`timetable` join keyed on session `user_id`):**
- `RoleDashboardApiController::teacherSummary()` (lines 195-246) — `my_classes`, `homework_to_review`, `assignments_to_grade`, `recent_circulars`, `students_by_class` all derive from `class_teacher.teacher_id = session('user_id')` (line 199) or a downstream `standardIds`/`divisionIds` list built from that join. This is the reference-correct pattern in the codebase.
- **Exception inside the same method:** `mySubjects` (lines 215-219) queries `subject` filtered only by `sub_institute_id`/`status`, with **no** `teacher_id`/`class_teacher` join — this returns every active subject in the school, not the teacher's own subjects. The Teacher dashboard's "Subjects" stat card and "My subjects" panel are both fed by this unscoped query.
- `TeacherAssignmentMobileApiController::standards()/divisions()` — `session()->get('user_id')` (line 4 in both, minified single-line methods) joined against `timetable.teacher_id`. Correctly scoped; gated by `api.session` middleware (`routes/api.php:41`).
- `TeacherDailyReportApiController` and `TeacherTransferApiController` — both cross-check the JWT payload's `id`/`sub_institute_id` against the request body (`authorizeRequest()`/`context()`, e.g. `TeacherDailyReportApiController.php:43-56`) and re-derive the actor's profile from the DB, then gate via `tblindividual_rights`/`tblgroupwise_rights` lookups keyed on the menu's `route_name` (e.g. `teachertransfer.index`). Well-built; not exploitable via a spoofed profile string.

**NOT scoped — confirmed gaps that leak or allow cross-teacher/cross-class access:**

1. **`ClassTeacherApiController`** (`api/ClassTeacherApiController.php`) — `authenticate()` (lines 16-35) only validates that the JWT is well-formed (`$this->jwtToken()->validate()`); it never reads an identity or role out of it. All CRUD methods scope purely by client-supplied `sub_institute_id`/`syear` (e.g. lines 61-64). **Route wiring confirmed**: `routes/api.php:249` — `Route::apiResource('class-teachers', ClassTeacherApiController::class)->except(['show']);` sits outside every `Route::middleware('api.session')` group in the file (the nearest groups close at lines 107, 112, 200, 206, 214 — all well before line 249). **Net effect: any holder of a valid JWT — including a teacher's own token — can create, update, or delete any class-teacher assignment for any teacher/class in the institute.** This is an admin-only action (§2.3) reachable without an admin role.
2. **`teacherapiController.php`** (lowercase; ~30 methods, wired via `routes/teacherapi.php:18` — `Route::controller(teacherapiController::class)->group(...)` with **no middleware at all**, not even `api.session`). Every method's only auth check is `$this->jwtToken()->validate()`; the acting `teacher_id`/`created_by` is taken directly from client input in every write method (e.g. `add_teacherStudentDisciplineAPI`, `add_teacherPTMStatus`, `add_teacherLessonPlanning`, `add_teacherExamSchedule`, `add_teachertaskAPI`, `add_teachercomplaintAPI`) and in reads like `get_teacherResourceAPI` (`where('v.created_by', $teacher_id)` with `$teacher_id` from the request). **Net effect: any authenticated caller can read or write records — resources, PTM status, discipline entries, lesson plans, exam schedules, tasks, complaints — attributed to an arbitrary other teacher**, an IDOR/impersonation pattern spanning the whole controller, not an isolated line.
3. **`api\lms\StudentHomeworkApiController`** — `index()` branches its scoping logic on a **client-supplied** `user_profile_name` string (`$request->input(...)`, line 21/48/50), not a session/JWT-derived value. If that field is omitted or sent as `"Admin"`, the query returns unscoped, institute-wide homework/subject data (lines 65-79, 558-590) — a caller can self-declare a broader role to widen what they see.
4. **`api\result\MarksEntryApiController`** — delegates to a legacy Blade-era controller (`result\marks_entry\marks_entry_controller`) via `standard`/`division`/`subject`/`exam` request params with no visible teacher-ownership check in the API layer itself. **[inferred / unresolved]** — the legacy delegate was not traced in this pass, so whether teacher-scoping happens deeper in the call chain is unconfirmed; flagging as an open question rather than a settled finding.

## 3. End-to-end workflow narrative

**1. Login → menu context.** After authentication, `AuthContext` populates `menuContext` (`sub_institute_id, user_id, user_profile_name, user_profile_id, client_id`); `useMenuRights.ts:116` uses it (falling back to `getStoredMenuContext()`, lines 78-98, reading `localStorage` under several legacy key names) to `POST /api/menu-rights` (line 131-143).

**2. Sidebar built.** The response's `level 1/2/3` arrays are normalized (`normalizeLevel`, lines 100-106) and passed to `buildMenuTree()` (`menuMappers.ts:192`), which filters by `status === 1` (line 198), hides a small hardcoded blocklist (`HIDDEN_MENU_LINKS`, lines 169-176 — e.g. `student_homework_submission.index`, `question_paper.index`), relabels one entry to "Exam" (`EXAM_MENU_LINKS`, lines 158-161), and resolves each `link` through `mapApiLinkToRoute()` — a ~900-line lookup table of legacy Laravel route-name → Next.js path mappings (`routeMapper.ts`). **What a teacher sees in the sidebar is 100% a function of what the backend's menu-rights response includes for that `user_profile_id`** — the frontend applies no additional teacher-specific filtering beyond the two blocklists above, which apply to everyone.

**3. Dashboard.** `app/dashboard/page.tsx:39` calls `resolveDashboardRole(ctx?.user_profile_name)` → `'teacher'` → renders `TeacherDashboard.tsx`, which calls `fetchTeacherDashboard` (`dashboard-api.ts:143-145`) → `POST /api/dashboard/teacher` (Next.js proxy, `app/api/dashboard/teacher/route.ts`) → forwards to Laravel `POST /api/teacher-dashboard/summary` (`routes/api.php:105`, behind `api.session` middleware) → `RoleDashboardApiController::teacherSummary()`.

## 4. Gap list — Teacher parity with Student workflow

**Note on baseline:** the Student workflow itself is far from fully built — of the 6 core student tasks audited, only 2 (homework/assignment summary, circulars) have any self-scoped implementation, both routed through the single `studentSummary` endpoint. Attendance, results, fees, and timetable have **no** student self-service page or `is_student`-scoped endpoint either. "Bring Teacher to parity with Student" therefore means parity with a partially-built reference, not a complete one — flagging this so priority-setting accounts for it.

Ordered by priority (daily classroom tasks first):

1. **Fix the three dead quick-action links** (`TeacherDashboard.tsx:63,65,66`) — `/attendance` → `/attendance/attendance_dashboard`, `/lms/assignment` → `/lms/lmsAnnotate_assignment`, `/general/circular` → `/front_desk/circular`. Zero backend work; highest-impact, lowest-effort fix in this entire audit.
2. **Scope the attendance page to the teacher's assigned classes** — `app/attendance/attendance_dashboard/page.tsx` currently lets a teacher pick any class; needs the same `class_teacher`-join scoping pattern `RoleDashboardApiController::teacherSummary` already uses, applied to whatever controller `attendance-api.ts` calls.
3. **Fix `mySubjects` scoping in `teacherSummary`** (`RoleDashboardApiController.php:215-219`) — join through `class_teacher`/a teacher-subject mapping table instead of returning every active subject in the institute. Follow the same join pattern already used for `myClasses` (lines 195-202).
4. **Build a "my timetable" web page for teachers** — the backend scoping already exists (`TeacherAssignmentMobileApiController::standards()/divisions()`), it just has no web consumer. Needs: a new frontend page (naming convention: likely `app/lms/teacher-timetable` or similar, alongside `teacher-diary`), a matching `routeMapper.ts` entry, and either reusing `TeacherAssignmentMobileApiController` via a new web-facing route or adding equivalent methods to `RoleDashboardApiController`.
5. **Add a teacher-scoped exam/marks entry surface** — currently `exam/marks-entry` and `result/marks-entry` are undifferentiated admin/exam-office consoles; no "marks entry restricted to my assigned subject+class" exists.
6. **Fix the `teacherapiController.php` and `ClassTeacherApiController` authorization gaps** (§2.2/§2.3) — these are correctness/security issues independent of the "parity" framing, but block trusting any future teacher-scoped feature built on `teacherapiController`'s ~30 methods, since none of them currently verify caller identity against the acted-upon `teacher_id`.
7. **Add a "fee dues for my class" view for teachers** — admin-adjacent, lower priority; no student equivalent exists either, so this is a net-new capability rather than a parity fix.
8. **Add self-service "my ID card" for both roles** — currently `teacher_icard`/`student_icard` are admin issuance tools only; no login-scoped "view my own card" page exists for either role.
9. **Resolve the `lmsPortfolioController.php:73` `" TEACHER"` typo** — small, isolated fix, low priority but easy.
10. **Investigate `app/classteacher/page.tsx`** — its actual content/role-gating wasn't confirmed in this pass; worth a follow-up read before building anything adjacent to it.
11. **Confirm/resolve the `tbluserprofilemaster` free-text risk (§2.1)** — not urgent unless a tenant is actually using a teacher-profile name other than "Teacher"/"Lms Teacher"; worth a data check against a real tenant's profile table before treating as inert.

## 5. Implementation plan (naming conventions only — no new patterns)
